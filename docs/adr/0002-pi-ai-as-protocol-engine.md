# 0002. 线协议由插件自带的 pi-ai 副本执行

## Status（状态）

Accepted。**已修订（2026-10-18）**：当时钉住的 `0.87.x` 已随上游发版走到 `~1.3.0`，`0.x` 语义的论证不再适用，见文末「修订」。

## Context（背景）

三种线协议的难点不在路由，而在 SSE 解析、工具调用增量、DeepSeek 系 `reasoning_content` 回放、thinking 档位映射与缓存字段——DSH 自己的 `llm-pi-ai` 用的正是 pi-ai。

## Decision（决策）

新插件的适配器自己钉住一份 `@earendil-works/pi-ai` 作为直接依赖（决策当时为 `0.87.x`），由插件决定升级节奏，而不是复用 Harness 运行时那份。理由：pi-ai 已经踩平上述难点。插件只管目录、路由、会话头与 UI。

代价与约束：插件因此与 pi-ai 的模型目录 JSON 结构、`Provider`/`Models` 类型和 compat 字段耦合；pi-ai 升级需要跑一遍兼容测试。当时的论证是：`0.x` 语义下 `^0.85.1` 不含 `0.86+`，所以"跟随 DSH 的 pin"永远拿不到上游修复，这正是必须自带副本的原因。

考虑过并否决：零第三方依赖、三协议自研（可控性最高，但要把上述难点重踩一遍，回归风险与工程量不可接受）；运行时从 CDN 拉 pi-ai 目录 JSON（少一次发版，但引入第三方 CDN 与包内部路径依赖）。

## Consequences（后果与影响）

- pi-ai 被**打进产物**（作为 devDependency 编译进 `lib/`），安装者不必再解析它，本插件对外没有运行时依赖。
- pi-ai 改请求构造即改变本插件的线上行为，且它的 opencode-go 内置目录是本插件协议判定的第 1 级证据（ADR-0004）；升级 pi-ai 必须重跑契约测试。
- 上游发版即可能改变目录结构与术语，因此本 ADR 只把版本号记为决策当时的基线。

## 修订（2026-10-18）：版本号与 `0.x` 语义

- 决策当时的 `0.87.x` 已过时：`package.json` 现在声明 `@earendil-works/pi-ai: ~1.3.0`（`README.md` 兼容性表同写 `~1.3.0`）。
- 「`0.x` 语义下 `^0.85.1` 不含 `0.86+`」的论证**不再适用**：pi-ai 已进入 `1.x`，现行范围是 `1.3.x` 内的 `~` 范围。
- 结论（自带副本、由插件决定升级节奏、打包进产物）不变；变的只是钉住的版本与范围写法。
